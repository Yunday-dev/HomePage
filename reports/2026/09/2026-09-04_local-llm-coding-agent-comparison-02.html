같은 Unity 작업으로
세 가지 코딩 에이전트를 비교했다

Qwen3.8-27B, Qwen3-Coder-Next 80B, Codex GPT-5.6 Sol에 동일한 Unity Hero 이동·공격 기능 구현을 맡겨 실제 작업 완성도를 비교했다. 단순 코드 생성 속도보다 컴파일, 테스트, 오류 복구, 실제 Play Mode까지 얼마나 스스로 끝까지 완성하는가를 기준으로 결과를 정리했다.

작업 목표

로컬에서 사용하는 Qwen 계열 모델과 상용 프론티어 코딩 에이전트가 실제 Unity 프로젝트에서 어느 정도 차이를 보이는지 같은 조건에서 확인하는 것이 목적이다.

비교에서 확인한 항목

  • 기존 코드베이스와 전투 구조를 얼마나 정확하게 이해하는가
  • 여러 파일이 연결된 기능을 기존 구조를 활용해 구현하는가
  • 코드를 작성한 뒤 실제 Unity 컴파일까지 확인하는가
  • 관련 테스트와 전체 회귀 테스트를 직접 실행하는가
  • 테스트가 실패했을 때 원인을 찾아 스스로 수정하고 다시 검증하는가
  • 최종적으로 실제 Play Mode에서 정상 동작하는가
  • 작업 완료까지 사용자 개입이 얼마나 필요한가

완료 기준

응답을 반환한 시점이 아니라 실제로 사용할 수 있는 상태까지 도달한 시점을 완료로 본다.

컴파일, 자동 테스트, 최종 diff 검증, 실제 동작 확인을 포함한다.

동일하게 수행한 작업

세 모델 모두 같은 시작 코드와 같은 요구사항을 사용했다. 비교 대상은 Hero를 플레이어가 직접 조작할 수 있도록 이동과 공격 명령을 추가하는 기능이다.

Hero 이동·공격 명령

  • Hero는 자동으로 적을 타겟으로 지정하거나 다른 적으로 자동 전환하지 않는다.
  • 적을 클릭하면 해당 적을 공격 대상으로 지정한다.
  • 빈 전장을 클릭하면 해당 월드 위치로 이동한다.
  • 지정한 적이 사라져도 다른 적을 자동으로 공격하지 않는다.
  • 일반 아군 유닛은 기존 자동 전투 동작을 유지한다.
  • UI 클릭은 이동·공격 명령으로 처리하지 않는다.
  • 기존 이동·공격·회피·분리·쿨다운·피해·사망 로직을 가능한 그대로 재사용한다.

왜 이 작업을 사용했나

입력, 카메라, UI, 전투, 이동, 타겟팅, 테스트가 동시에 연결돼 있어 단순한 코드 생성보다 기존 프로젝트 이해와 회귀 영향 관리를 함께 평가할 수 있기 때문이다.

Codex에서 가장 인상적이었던 부분

14분 41초라는 속도보다 더 중요한 차이는 작업 중 문제가 발생했을 때의 행동이었다.

40개 테스트 실패를 작업 중 직접 발견

첫 전체 테스트 실행에서 40개가 실패했지만 이를 완료로 처리하지 않았다. 실패 원인이 기존 테스트 fixture에서 Hero를 일반 자동 전투 actor로 사용하던 구조에 있다는 점을 찾아냈다.

기존 테스트 의도를 유지하면서 복구

공유 전투 로직을 검증하는 기존 fixture는 명시적으로 자동 모드를 유지하도록 조정하고, 실제 runtime Hero 동작은 별도 Hero 테스트에서 검증하도록 분리했다.

완료 조건을 실제로 실행

Unity 6000.4.11f1을 이용해 runtime과 test assembly를 컴파일하고, 관련 테스트 12개와 전체 272개 테스트를 모두 실행한 뒤 git diff --check까지 확인했다.

추가 지시 없이 실제 동작까지 일치

자동 검증이 끝난 뒤 Unity Game View에서 Hero 이동과 적 공격을 직접 확인했으며, 별도의 수정 요청 없이 첫 실행에서 정상 동작했다.

관찰: 이번 작업에서 프론티어 코딩 에이전트의 차이는 “더 좋은 코드를 처음부터 생성한다”는 것보다 실패를 발견하고, 원인을 좁히고, 수정하고, 다시 검증해 스스로 완료 상태까지 도달하는 능력에서 더 크게 나타났다.

이번 비교에서 확인한 점

1

로컬 LLM도 실제 개발에 사용할 수 있다

Qwen3.8-27B는 속도와 작업 효율에서는 Codex보다 뒤졌지만, 실제 Unity 기능을 구현하고 자동 테스트와 Play Mode까지 통과할 수 있다는 점을 확인했다.

2

큰 코딩 특화 모델이 항상 더 안정적인 것은 아니다

Qwen3-Coder-Next 80B는 256K 컨텍스트와 빠른 구현이라는 장점이 있었지만, 이번 작업에서는 컴파일과 테스트 검증의 신뢰성이 부족했다.

3

프론티어 모델의 강점은 작업 완결성에 있었다

Codex는 구현 도중 발생한 대규모 테스트 실패까지 스스로 복구한 뒤 사용자 개입 없이 최종 정상 상태에 도달했다.

4

가장 중요한 지표는 Time-to-valid-solution

빠른 응답이나 높은 토큰 속도보다 실제로 컴파일되고 테스트를 통과하며 동작 가능한 결과까지 도달하는 시간이 개발 생산성에 더 직접적이었다.

다음 방향

이번 비교를 통해 로컬 모델과 프론티어 모델을 서로 대체 관계로 보기보다, 비용과 작업 난이도에 따라 역할을 나누는 편이 현실적이라는 판단을 얻었다.

1

일상적인 반복 작업은 로컬 LLM

코드 탐색, 작은 기능 추가, 명확한 수정, 반복 작업처럼 충분히 검증된 범위는 Qwen3.8-27B를 활용해 로컬에서 처리한다.

2

복잡하고 회귀 위험이 큰 작업은 Codex

여러 시스템이 연결되거나 실패 복구가 중요한 작업, 짧은 시간 안에 높은 완성도가 필요한 작업은 프론티어 코딩 에이전트를 활용한다.

운영 방향

로컬 LLM은 사용량 제약 없이 반복적으로 사용할 수 있다는 장점이 있고, Codex는 제한된 사용량을 소비하는 대신 복잡한 작업을 훨씬 빠르고 안정적으로 끝내는 장점이 있다. 앞으로는 한쪽을 완전히 대체하기보다 작업 난이도에 따라 적절한 모델로 승격하는 방식을 사용한다.
