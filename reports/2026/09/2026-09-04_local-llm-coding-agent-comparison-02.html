작업 목표

로컬 LLM과 Codex의 서로 다른 모델·추론 설정이 실제 Unity 기능 구현에서 어느 정도의 작업 완성도 차이를 보이는지 같은 조건으로 비교했다.

비교 기준

  • 기존 코드베이스와 전투 구조를 정확하게 이해하는가
  • 기존 이동·공격 로직을 재사용해 기능을 연결하는가
  • Unity 컴파일을 실제로 통과하는가
  • 관련 테스트와 전체 EditMode 테스트를 실행하는가
  • 테스트 실패를 발견했을 때 스스로 수정하고 다시 검증하는가
  • 실제 Play Mode에서 정상 동작하는가
  • 사용자 개입 없이 완료 상태까지 도달하는가

핵심 지표

Time-to-valid-solution

모델이 답변을 끝낸 시점이 아니라 실제 프로젝트에서 사용할 수 있는 상태에 도달했는지를 우선한다.

동일하게 수행한 작업

네 번의 실행 모두 같은 시작 코드와 같은 요구사항을 사용했다. 비교 대상은 Hero에 플레이어 직접 이동·공격 명령을 추가하는 기능이다.

Hero 이동·공격 명령

  • Hero는 자동으로 적을 타겟으로 지정하거나 다른 적으로 자동 전환하지 않는다.
  • 적 또는 Boss를 클릭하면 해당 대상을 공격 대상으로 지정한다.
  • 빈 전장을 클릭하면 현재 공격 대상을 해제하고 해당 위치로 이동한다.
  • 지정한 적이 사라지거나 죽어도 다른 적을 자동으로 공격하지 않는다.
  • 일반 아군 유닛은 기존 자동 타겟팅과 전투 동작을 유지한다.
  • UI 클릭과 Playing 상태가 아닌 입력은 명령으로 처리하지 않는다.
  • 기존 이동·접근·회피·분리·쿨다운·피해·사망 경로를 가능한 그대로 재사용한다.

왜 이 작업을 사용했나

입력, 카메라, UI, 전투, 이동, 타겟팅, 테스트가 동시에 연결되어 있어 모델의 단순 코드 생성 능력보다 저장소 이해와 회귀 영향 관리를 함께 볼 수 있기 때문이다.

실행 결과

1

Qwen3.8-27B · 128K

VALID

코드베이스 조사와 구현 전환은 느렸고 작업 중 Compaction이 발생했다. 그러나 관련 테스트와 전체 회귀 테스트를 통과했고, 실제 Play Mode에서 발견한 입력 시스템 문제까지 수정해 최종 동작 상태에 도달했다.

결과: 43m 20s · Compaction 2회 / 3m 33s · Hero 테스트 12/12 PASS · 전체 EditMode 272/272 PASS · Play Mode PASS
2

Qwen3-Coder-Next 80B · 256K

INCOMPLETE

256K 컨텍스트에서 Compaction 없이 빠르게 구현했지만 완료 보고 이후 Unity 컴파일 오류가 확인됐다. 오류를 전달해 수정하게 한 뒤에도 다른 컴파일 오류가 남아 실제 테스트 단계까지 도달하지 못했다. 

1차: CS1503 — Argument 3 type mismatch
2차: CS0246 — List<> type could not be found
결과: 19m 05s+ · Compaction 0회 · Compile FAIL × 2 · EditMode 테스트 미실행 · 유효 결과 미도달
3

Codex · GPT-5.6 Sol · xhigh

VALID · NO INTERVENTION

한 번의 요청으로 구현부터 검증까지 진행했다. 첫 전체 EditMode 실행에서 40개 실패를 직접 발견하고, 기존 테스트 fixture가 Hero를 일반 자동 전투 actor로 사용하던 원인을 찾아 수정한 뒤 전체 테스트를 다시 통과시켰다.

Codex 표시: Worked for 14m 41s · 사용자 개입 0회 · Hero 테스트 12/12 PASS · 전체 EditMode 272/272 PASS · Unity Compile PASS · git diff --check PASS

Play Mode: 첫 실행부터 Hero 이동과 적 공격이 정상 동작했다.

4

Codex · GPT-5.6 Terra · high

VALID · NO INTERVENTION

같은 작업을 더 가벼운 Codex 설정으로 다시 수행했다. 구현 과정에서 기존 테스트 20개가 실패했지만, Hero를 identity로 제외하던 조건이 원인임을 찾아 자동 타겟팅이 비활성화된 Combatant만 필터링하도록 수정했다.

Codex 표시: Worked for 10m 46s · 사용자 개입 0회 · CombatDirectorTests 117/117 PASS · broader EditMode 269/269 PASS · git diff --check PASS

마지막으로 입력/query 관련 assertion 두 개를 추가한 뒤의 최종 batch rerun은 코드나 테스트 실패가 아니라 로컬 Unity licensing-client 문제로 실행되지 못했다.

Play Mode: Terra high 역시 첫 실행부터 Hero 이동과 적 공격이 정상 동작했다.

Terra High 결과가 의미 있었던 이유

Sol xhigh보다 가벼운 설정에서도 동일한 Unity 기능을 사용자 개입 없이 완성했고, 중간 테스트 실패까지 스스로 복구했다.

1

20개 실패를 그냥 넘기지 않았다

기존 테스트가 Hero를 객체 identity 기준으로 제외하던 부분을 찾아 실제 의미인 자동 타겟팅 활성 여부를 기준으로 수정했다.

2

광범위 테스트까지 직접 실행했다

Focused 수준에 머물지 않고 CombatDirectorTests 117/117과 broader EditMode 269/269를 통과했다.

3

실제 Play Mode도 정상

자동 검증 결과와 별개로 실제 Unity에서 Hero 이동·공격을 확인했고 첫 실행부터 정상 동작했다.

4

Sol xhigh가 항상 필요한 것은 아니다

요구사항이 명확하고 테스트 가능한 중대형 기능이라면 Terra high도 충분한 작업 완성도를 보여줄 수 있다는 실사용 데이터를 얻었다.

이번 비교에서 확인한 점

1

로컬 LLM도 실제 개발에 사용할 수 있다

Qwen3.8-27B는 느렸지만 실제 기능 구현, 자동 테스트, Play Mode까지 도달해 반복적으로 사용할 수 있는 실용적인 로컬 코딩 모델임을 확인했다.

2

큰 모델이 항상 더 안정적인 것은 아니다

Qwen3-Coder-Next 80B는 큰 컨텍스트와 빠른 구현 장점이 있었지만 이번 작업에서는 컴파일·테스트 검증 신뢰성이 부족했다.

3

Codex의 강점은 자가 검증과 복구였다

Sol과 Terra 모두 중간에 발생한 다수의 테스트 실패를 스스로 발견하고 원인을 수정한 뒤 정상 상태까지 진행했다.

4

일반적인 중대형 작업에는 Terra high가 유력하다

이번 Hero 기능 정도의 난이도에서는 Terra high도 사용자 개입 없이 정상 동작 결과에 도달했다. Sol xhigh는 더 어려운 문제를 위한 상위 단계로 남겨두는 편이 효율적일 가능성이 높다.
