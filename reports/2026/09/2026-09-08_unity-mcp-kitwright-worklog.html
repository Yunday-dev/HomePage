Unity MCP를 실제로 써보고
최소 구성으로 정리하다

RTX 5090에서 구동하는 Qwen3.8-27B와 OpenCode에 KitWright Unity MCP를 연결해 실제 Unity 개발에 사용해봤다. MCP가 있으면 작업 흐름이 크게 빨라질 것으로 기대했지만, 실제로는 구현 과정이나 작업 왕복이 눈에 띄게 줄었다는 체감은 크지 않았다. 오히려 처음에는 너무 많은 MCP 도구를 열어둔 탓에 에이전트가 필요 이상의 검사와 테스트를 수행하면서 작업 시간이 길어졌다. 이후에는 장점이 확실했던 부분만 남기고 최소 MCP 구성으로 운용하기로 했다.

작업 배경

Unity MCP라는 방식이 실제 로컬 코딩 에이전트 작업에 얼마나 도움이 되는지 궁금해서 KitWright Unity MCP를 설치하고 OpenCode + Qwen3.8-27B 개발 흐름에 연결했다. Scene이나 Inspector 같은 Unity Editor 상태를 직접 다룰 수 있다는 점은 분명 흥미로웠지만, 실제 작업에서 얼마나 큰 차이가 나는지는 직접 써봐야 판단할 수 있다고 봤다.

확인하고 싶었던 것: MCP가 단순히 “가능한 기능을 늘리는 것”을 넘어, 실제 Unity 기능 구현 시간을 줄이고 에이전트 작업 흐름을 더 자연스럽게 만드는지 확인하는 것이었다.

KitWright Unity MCP 설치

Unity 프로젝트에 KitWright Unity MCP를 설치하고 OpenCode와 연결했다. 기존에는 파일과 Unity batch 실행을 중심으로 작업했다면, MCP 연결 후에는 실행 중인 Unity Editor의 일부 상태와 기능을 에이전트가 직접 사용할 수 있게 됐다.

처음에는 오히려 작업 시간이 길어졌다

처음에는 사용할 수 있는 MCP 기능을 많이 열어둔 상태로 작업했다. 도구가 많으면 에이전트가 상황에 맞는 기능을 골라 더 효율적으로 움직일 것이라고 생각했지만, 실제로는 필요하지 않은 검사와 테스트까지 수행하면서 작업 시간이 크게 늘어나는 경우가 있었다.

SLOW
전체 작업 시간

MCP를 연결하지 않았을 때보다 오히려 오래 걸리는 작업도 있었다.

실제 체감: MCP를 연결했다고 해서 구현 과정의 왕복이나 전체 작업 시간이 크게 줄어든다는 느낌은 아직 크지 않았다. 오히려 너무 많은 MCP를 열어두면 에이전트가 과잉 검증을 하는 비용이 더 크게 느껴졌다.

그래서 최소 MCP만 켜두기로 했다

이후에는 모든 기능을 항상 열어두는 대신, 평소 작업에 필요한 최소한의 MCP만 활성화하는 방식으로 바꿨다. 특정 Editor 기능이 실제로 필요한 작업이 생기면 그때 해당 MCP를 추가로 켜는 방식이다.

1

기본은 최소 구성

Default

일상적인 코드 수정과 검증에 필요한 최소 도구만 유지한다.

2

필요한 기능만 추가

On Demand

Prefab, Material, Scene 편집처럼 특정 MCP 기능이 필요한 작업에서만 추가로 활성화한다.

3

도구 선택 범위를 작게 유지

Lean

에이전트가 불필요한 검사 경로로 빠지는 것을 줄이는 것을 우선한다.

실제로 켜둔 최소 MCP 도구

모든 Unity MCP 기능을 열어두는 대신, 현재 개발 흐름에서 자주 쓰는 Editor 상태 확인·기본 오브젝트 조회·Play Mode·테스트·화면 확인 기능만 남겼다. 나머지 MCP는 항상 켜두지 않고 실제 작업에서 필요할 때만 추가로 활성화한다.

MCP 도구 용도
get_editor_state현재 Unity Editor 상태 확인
get_console_errors컴파일 오류와 Console 오류 확인
find_gameobjectScene 안의 필요한 GameObject 탐색
inspect_componentComponent 상태와 값 확인
inspect_serialized_referencesInspector의 serialized reference 확인
edit_serialized_reference필요한 reference 연결·수정
enter_playmode현재 Editor에서 Play Mode 시작

run_tests필요한 Unity 테스트 실행
capture_gameviewGame View 결과 확인
운용 원칙: 이 도구들조차 매 작업에서 전부 사용할 필요는 없다. 에이전트가 불필요한 검사와 테스트로 빠지지 않도록 필요한 MCP만 사용하고, 추가 도구는 해당 작업이 요구할 때만 연다.

그래도 한 가지는 확실히 편해졌다

MCP를 연결하기 전에는 Unity가 이미 실행 중인 상태에서 에이전트가 테스트나 batch 실행을 시도할 때 현재 실행 중인 Unity Editor를 종료할지 묻는 경우가 반복됐다. 실제 개발 중인 Editor를 계속 열어두고 싶은 입장에서는 이 확인 과정이 꽤 번거로웠다.

MCP 연결 전

  • 실행 중인 Unity가 있으면 종료 여부를 묻는 경우가 있었다.
  • 테스트를 위해 Editor lifecycle을 사용자가 직접 판단해야 했다.
  • 코딩 에이전트 작업 흐름이 중간에 끊기는 일이 있었다.

MCP 연결 후

  • 현재 실행 중인 Unity Editor를 그대로 유지할 수 있다.
  • Editor를 끌지 묻는 확인이 사라져 작업 흐름이 단순해졌다.
  • 이 부분은 MCP를 계속 유지할 이유로 충분히 체감됐다.
현재 가장 분명한 장점: MCP가 개발 속도를 크게 높였다기보다, 이미 실행 중인 Unity Editor를 유지한 채 에이전트 작업을 계속할 수 있게 된 점이 가장 실용적이었다.

현재 운용 방식

Unity MCP를 직접 사용해본 결과, 현재 단계에서는 “MCP를 연결했으니 최대한 많이 사용한다”는 방향은 맞지 않았다. 작업 속도 면에서 큰 차이는 아직 체감하지 못했고, 모든 MCP를 열어두면 오히려 불필요한 검사와 테스트 때문에 시간이 늘어날 수 있었다.

정리

  • Unity MCP가 실제 개발 흐름에 어떤 차이를 만드는지 확인하기 위해 KitWright MCP를 설치했다.
  • 작업 왕복이나 구현 시간이 크게 줄어든다는 체감은 아직 크지 않았다.
  • 처음에는 너무 많은 MCP를 열어둔 탓에 에이전트가 필요 이상의 검사와 테스트를 수행해 오히려 시간이 오래 걸렸다.
  • 이후 기본 MCP 구성을 최소화하고, 필요한 기능은 작업별로 추가하는 방식으로 변경했다.
  • 기본 구성에는 get_editor_state, get_console_errors, find_gameobject, inspect_component, inspect_serialized_references, edit_serialized_reference, enter_playmode, exit_playmode, run_tests, capture_gameview만 남겼다.
  • MCP 연결 후에는 실행 중인 Unity Editor를 종료할지 반복해서 묻는 흐름이 사라진 점이 가장 분명하게 편해졌다.
현재 결론: Unity MCP는 당장 개발 속도를 크게 높여주는 도구라기보다, 실행 중인 Unity Editor와 에이전트를 자연스럽게 연결해주는 보조 도구로 사용한다. 평소에는 최소 기능만 켜두고, 추가 MCP는 필요할 때만 활성화한다.
