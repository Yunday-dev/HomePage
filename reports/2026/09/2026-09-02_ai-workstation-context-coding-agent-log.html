코딩 에이전트로 실제 코드 수정 및 64K와 128K Context 비교 벤치마킹

전날 구축한 RTX 5090 로컬 AI 추론 환경을 실제 Unity 개발에 투입했다. 가장 중요한 목표는 로컬 코딩 에이전트가 기존 프로젝트의 규칙을 이해하고 코드를 직접 수정한 뒤 테스트와 diff 검증까지 끝낼 수 있는지 확인하는 것이었다. 그 다음으로 64K와 128K Context가 같은 종류의 Agent 작업에 어떤 차이를 만드는지 비교했고, 작업 과정에서 드러난 권한·파일 소유권 문제도 함께 정리했다.

작업 배경

전날까지는 MacBook의 OpenCode가 LAN을 통해 Windows RTX 5090의 로컬 모델을 호출하고 Unity 저장소를 읽어 구조를 분석하는 단계까지 확인했다. 오늘은 여기서 한 단계 더 나아가 “코드를 읽는 로컬 LLM”을 “실제 작업을 끝내는 코딩 에이전트”로 사용할 수 있는지 검증했다.

가장 중요한 검증 — 실제 프로젝트 코드 수정

샘플 파일을 새로 만드는 대신 현재 Unity 프로젝트의 기존 생산 규칙을 이용해 CanProduce(UnitType) 형태의 유닛 생산 가능 여부 조회용 API를 추가하는 작업을 맡겼다.

이 API는 현재 자원과 게임 상태를 확인해 생산 가능 여부만 반환하고, Food 차감·Population 변경·유닛 생성·HUD 출력처럼 게임 상태를 바꾸는 동작은 하지 않는다. 기존 TryProduce 계열의 규칙을 재사용하도록 해 실제 프로젝트 구조를 이해해야만 안전하게 수정할 수 있는 작은 기능을 테스트 대상으로 삼았다.

평가 기준: 답변을 잘 만드는지가 아니라 기존 코드 분석 → 최소 수정 → 테스트 작성 → Unity 실행 → 실패 복구 → Git diff 확인까지 스스로 완료하는지를 본다.

구축 타임라인

오늘 작업은 중요도 순으로 재구성했다. 핵심은 “실제 코드 수정”, 그 다음이 “Context 비교”, 마지막이 “개발 환경 안정화”다.

1

실제 Unity 코드 수정 작업 선정

Core

현재 생산 시스템을 건드리는 작은 기능으로 CanProduce(UnitType) 조회 API를 선택했다. 단순 예제보다 실제 구조를 읽어야 하지만, 구현 범위는 작아서 모델·Context 비교에 적합한 기준 작업으로 사용할 수 있다.

2

Read → Edit → Test → Diff Agent loop 검증

Coding Agent

Agent가 관련 문서와 C# 코드를 읽고 구현을 추가한 뒤, focused EditMode 테스트와 전체 EditMode suite를 실행하고 git diff --check까지 확인하도록 했다.

결과: 로컬 27B 모델이 단순 코드 제안이 아니라 실제 저장소에서 수정과 자동 검증까지 수행할 수 있음을 확인했다.

3

64K Context baseline

Benchmark

65,536 Context에서 기준 작업을 수행했다. 기능 구현과 전체 테스트는 완료했지만 작업 중 Compaction이 한 번 발생했다.

의미: 64K도 작은 실전 작업을 끝낼 수 있지만, 문서·코드·테스트를 함께 읽는 Agent loop에서는 이미 Context 압박이 나타나기 시작했다.

4

128K Context 비교

Benchmark

같은 모델을 131,072 Context로 올려 동일 계열 작업을 다시 수행했다. 이 작업에서는 Compaction 없이 완료했고 최종 활성 Context가 약 82.8K까지 사용됐다.

현재 해석: 64K는 짧은 수정용으로 충분할 수 있지만, 여러 파일과 테스트를 오가는 자율 작업에서는 128K가 더 넉넉한 기본 프로필 후보가 된다.
5

OpenCode 권한 및 파일 소유권 이슈 추적

Stability

초기 권한 오류를 피하기 위해 관리자 권한으로 Agent를 실행했던 과정에서 Unity가 생성한 일부 파일까지 관리자 소유가 되는 문제를 확인했다.

조치: OpenCode 사용자 디렉터리와 프로젝트 파일 소유권을 정상 사용자로 복구하고, 이후 OpenCode·Unity·Git은 관리자 권한 없이 실행하는 것을 기준으로 정리했다.

결과: Agent가 파일을 생성하거나 Unity batchmode를 실행해도 프로젝트 소유권이 뒤섞이지 않는 기준점을 확보했다.

운영 방식 변경점

기존 Mac 개발 환경 ↔ Windows 추론 서버 구조 자체는 유지했다. 오늘은 모델을 어떤 역할로 부를지와 Windows에서 모델 서버를 다루는 방법을 추가로 정리했다.

FAST / DEEP 용어 정리

FAST는 일상적인 코드 수정, 반복 테스트, 짧은 분석처럼 속도와 즉시성이 중요한 작업을 맡기는 로컬 모델 프로필이다. 현재 기준 모델은 RTX 5090 VRAM 안에 올라가는 Qwen3.8-27B Q4_K_M이다.

DEEP는 더 많은 구조 이해, 복잡한 리팩터링, 장시간 Agent 작업처럼 모델 품질이 더 중요한 작업을 위한 상위 프로필이다. 향후 더 큰 코딩 모델을 GPU + RAM offload로 비교해 실제 생산성 향상이 있는지 검증한다.

중요: FAST와 DEEP는 모델 이름이 아니라 업무 역할을 구분하는 운영 프로필 명칭이다.

PowerShell $PROFILE에 모델 제어 함수 등록

Windows PowerShell의 $PROFILE에 모델별 시작·종료 명령을 PowerShell 함수로 등록했다. “시스템 함수”보다는 PowerShell 프로필 함수라고 부르는 것이 정확하다.

매번 긴 llama-server 실행 옵션을 입력하지 않고 FAST/DEEP 프로필에 필요한 모델·Context·GPU 설정을 함수 호출로 올리고 내릴 수 있게 해 운영 작업을 단순화했다.

# 개념적인 운영 형태
PowerShell 시작
  └─ $PROFILE 자동 로드
      ├─ FAST 모델 시작 함수
      ├─ DEEP 모델 시작 함수
      └─ 현재 llama-server 종료 함수

API Key와 네트워크 식별 정보 등 공개할 필요가 없는 값은 Work Log에 기록하지 않는다.

다음 작업

작은 조회 API는 통과했다. 다음에는 입력·카메라·이동·타깃·공격 시스템이 함께 연결되는 조금 더 복잡한 실제 기능으로 Agent 능력을 확인한다.

1

플레이어 이동·공격 명령 구현

전투 화면의 빈 공간을 클릭하면 플레이어 캐릭터가 해당 위치로 이동하고, 적을 클릭하면 그 적을 공격 대상으로 지정하도록 만든다.

단순 조회 함수와 달리 입력 처리, UI 클릭 구분, 화면 좌표→월드 좌표 변환, 이동 상태, 공격 타깃, 기존 자동 전투와의 분리가 동시에 필요하다.

2

복잡한 작업에서 64K / 128K 재비교

동일 baseline과 동일 prompt로 복잡한 기능을 각각 수행시켜 Context 사용량, Compaction 횟수·시간, 전체 작업 시간, 테스트 재시도, 과잉 탐색 여부와 최종 구현 품질을 비교한다.

3

실제 Play Mode 검증 포함

EditMode 테스트만으로 잡기 어려운 마우스 입력·카메라·UI raycast 문제를 확인하기 위해 실제 Game View에서 동작하는지 수동 또는 Play Mode 검증 단계를 추가한다.

4

DEEP 모델 후보 비교 준비

FAST 27B의 기준 데이터를 충분히 모은 뒤 더 큰 코딩 모델이 복잡한 Unity 작업에서 탐색량과 Compaction을 줄이고 설계·복구 품질을 높이는지 비교한다.
