128K Context와 실제 코드 수정 검증

전날 구축한 RTX 5090 로컬 AI 추론 서버를 실제 개발 워크플로에 투입했다. 오늘의 목표는 “저장소를 읽을 수 있다”에서 한 단계 더 나아가, 로컬 코딩 에이전트가 작은 Unity 기능을 직접 수정하고 테스트까지 마칠 수 있는지 확인하고, 동시에 64K와 128K Context가 긴 Agent 작업에 어떤 차이를 만드는지 측정하는 것이었다.

Server: Windows + RTX 5090 32GB Client: MacBook Pro Runtime: llama.cpp / llama-server Model: Qwen3.8-27B Q4_K_M Context: 64K → 128K Agent: OpenCode Target: Unity Edit / Test Loop
작업 배경현재 상태구축 타임라인아키텍처다음 작업운영 방향

작업 배경

전날에는 MacBook의 OpenCode가 LAN을 통해 Windows RTX 5090의 로컬 모델을 호출하고 실제 Unity 저장소를 읽는 단계까지 확인했다. 오늘은 로컬 Agent를 “분석 도구”에서 “실제 개발 도구”로 한 단계 확장하는 작업에 집중했다.

오늘 확인하려는 것

  • 코드 수정: Agent가 기존 아키텍처를 읽고 최소 범위의 C# 변경을 직접 만들 수 있는가?
  • 자동 검증: 수정 후 Unity EditMode 테스트와 Git diff 검증까지 이어갈 수 있는가?
  • Context 규모: 실제 repository 작업에서 64K가 충분한지, 128K가 실질적인 이점을 주는지 확인한다.
  • 개발 환경 안정성: Agent, Unity, Git이 모두 일반 사용자 권한에서 안전하게 동작하도록 권한 상태를 정리한다.

작업 원칙

Windows는 계속 추론 전용 서버 역할만 맡고, 프로젝트 파일·Unity·Git·Agent는 MacBook에 둔다. 로컬 모델은 HTTP API를 통해 필요한 코드와 도구 출력만 전달받는다.

공개 기록 원칙: 사설 네트워크 주소, 인증 키, 내부 프로젝트 식별 정보는 Work Log에서 제외하고 구조와 검증 결과만 기록한다.

구축 타임라인

오늘은 인프라를 새로 만드는 것보다, 전날 만든 환경을 안전하게 정리하고 실제 개발 작업으로 검증하는 데 시간을 사용했다.

1

Agent 실행 권한 정상화

Stability

문제: 초기 권한 오류를 우회하기 위해 관리자 권한으로 실행했던 Agent가 프로젝트와 사용자 설정 영역에 비정상 소유 파일을 남길 수 있다는 점을 확인했다.

조치: Agent 설정 디렉터리와 프로젝트 파일의 소유권을 정상 사용자로 복구하고, 이후 Agent를 일반 권한으로만 실행하도록 고정했다.

결과: Unity, Git, OpenCode가 동일한 사용자 권한으로 동작하는 안전한 개발 기준점을 확보했다.

2

64K 실제 Coding Agent baseline

Benchmark

동일한 기준 커밋에서 작은 Unity 기능 추가 작업을 수행했다. Agent는 문서와 관련 코드를 읽고, 기능을 추가하고, 테스트를 작성한 뒤 Unity EditMode suite와 git diff --check까지 실행했다.

관측: 작업 자체는 성공했지만 긴 tool loop 안에서 Context Compaction이 한 번 발생했다.

3

작은 비파괴 Query API 추가

Code

실제 프로젝트에 “현재 특정 항목을 생성할 수 있는가?”를 확인하는 읽기 전용 API를 추가했다. 기존 생성 규칙을 재사용하면서 자원 소비, 개체 생성, HUD 피드백 등 게임 상태 변경은 발생하지 않도록 구성했다.

의미: 로컬 Agent가 단순 예제 파일이 아니라 기존 시스템의 규칙을 보존한 채 실제 C# 변경을 만들 수 있음을 확인했다.

4

Unity 테스트와 Git 정리까지 자동화

Validation

새 기능에 대한 focused EditMode 테스트와 기존 전체 EditMode suite를 실행하고, Unity가 자동 생성한 부수 파일 변경을 식별해 최종 diff에서 제거했다.

결론: Read → Edit → Shell → Test → Diff Review로 이어지는 최소한의 Coding Agent loop가 실제 프로젝트에서 동작했다.

5

Context

6

64K vs 128K 결과 정리

Result

작은 실제 기능 구현에서는 64K도 완료 가능했지만 Compaction이 발생했고, 128K에서는 같은 종류의 Agent loop를 더 넉넉한 Context로 유지할 수 있었다.

현재 판단: 짧은 수정은 64K로도 충분하지만, 여러 파일을 읽고 테스트·복구까지 이어지는 자율 작업에서는 128K가 더 안정적인 FAST profile 후보가 된다.

오늘 확정한 원칙

  • Agent는 일반 사용자 권한으로 실행
  • 프로젝트는 Mac에 유지
  • 5090은 추론 전용으로 사용
  • Context 설정은 서버와 Agent 양쪽을 동일하게 맞춤
  • 실제 작업 평가는 답변 품질이 아니라 수정·테스트·복구 완료 여부로 판단

다음 작업

작은 비파괴 API 추가를 통과했으므로, 다음에는 여러 게임 시스템이 동시에 연결되는 조금 더 복잡한 작업으로 Agent의 실전 능력을 확인한다.

1

플레이어 이동·공격 명령 구현

화면에서 클릭한 위치로 플레이어 캐릭터를 이동시키고, 적을 클릭했을 때는 해당 대상을 공격하도록 만드는 기능을 구현한다.

입력 처리, UI 클릭 구분, 화면 좌표→월드 좌표 변환, 이동 상태, 공격 타깃 지정, 기존 자동 전투와의 분리까지 여러 시스템이 연결되는 작업이므로 오늘의 Query API보다 한 단계 복잡한 실전 테스트가 된다.

2

64K / 128K 동일 작업 A/B

동일 baseline과 동일 prompt에서 이동·공격 기능을 각각 실행해 Context 사용량, Compaction 횟수, 전체 작업 시간, tool call, 테스트 성공률과 과잉 탐색 여부를 비교한다.

3

실제 Play Mode 검증 강화

EditMode 테스트뿐 아니라 마우스 입력처럼 런타임에서만 드러나는 문제도 확인할 수 있도록 Play Mode 또는 실행 중 Editor 검증 흐름을 추가한다.

4

80B DEEP profile 준비

27B / 128K의 기준 데이터를 확보한 뒤 Qwen3-Coder-Next 80B 계열을 GPU + RAM offload로 실행해, 더 큰 모델이 복잡한 Unity 작업에서 탐색 효율과 설계 품질을 실제로 개선하는지 비교한다.
