RTX 5090으로
로컬 코딩 AI 에이전트 개발 환경 구축

Windows 데스크탑의 RTX 5090을 로컬 LLM 추론 서버로 사용하고, 실제 Unity 개발은 MacBook Pro에서 계속 진행하는 개인용 AI Workstation을 구축했다. 목표는 단순히 로컬 모델을 실행하는 것이 아니라, Mac의 개발 도구와 프로젝트를 유지한 채 OpenCode가 Windows의 GPU 추론을 사용할 수 있는 구조를 만드는 것이었다. 이날은 Qwen3.8-27B를 CUDA로 서빙하고 OpenCode를 연결한 뒤, 실제 Unity 저장소를 읽고 분석하는 단계까지 확인했다.

작업 목표

이번 작업은 RTX 5090을 단순한 로컬 LLM 실행 장치가 아니라 Unity 개발을 보조하는 로컬 코딩 AI 에이전트용 추론 서버로 구성하는 것이 핵심이다.

개발 환경과 추론 환경을 분리한다

Unity 프로젝트, Rider, Git, OpenCode는 기존처럼 MacBook Pro에서 사용한다. Windows PC는 RTX 5090에 모델을 적재하고 llama-server를 통해 추론 API만 제공한다.

핵심 구조: MacBook은 코드와 개발 도구를 담당하고, Windows RTX 5090은 모델 추론을 담당한다. 프로젝트 파일을 서버로 옮기지 않고 LAN API로 두 환경을 연결한다.

작업 과정

최종 구조를 바로 만든 것이 아니라, 런타임 선택부터 CUDA 전환, 모델 서빙, 네트워크 연결, OpenCode 인증까지 단계적으로 문제를 분리하며 구성했다.

1

로컬 LLM 런타임 선택

Runtime

LM Studio, Ollama, llama.cpp를 비교한 뒤 RTX 5090의 GPU layer, Context, KV cache와 향후 offload 설정을 직접 제어하기 쉬운 llama.cpp를 메인 런타임으로 선택했다.

2

Vulkan 설치본에서 CUDA 빌드로 전환

CUDA

처음 설치한 llama.cpp가 Vulkan backend로 동작하는 것을 확인했다. NVIDIA GPU 전용 추론 서버라는 목적에 맞춰 Vulkan 설치본을 제거하고 Windows x64 CUDA 빌드를 직접 설치했다. 

.\llama-cli.exe --list-devices
CUDA0: NVIDIA GeForce RTX 5090
3

드라이버와 CUDA 실행 환경 정리

Driver

NVIDIA 드라이버를 업데이트한 뒤 NVIDIA-SMI 616.56, CUDA UMD 13.4 환경에서 RTX 5090 CUDA backend가 정상 동작하는 것을 확인했다.

4

Qwen3.8-27B Q4_K_M 적재와 성능 확인

Model

첫 로컬 코딩 모델은 약 19GB 규모의 Qwen3.8-27B Q4_K_M으로 선택했다. RTX 5090 32GB 안에 모델을 적재하면서 Context와 런타임 버퍼를 위한 여유를 남길 수 있는 크기였다.

5

llama-server로 API 제공

Server

CLI에서 모델 성능을 확인한 뒤, MacBook의 OpenCode가 호출할 수 있도록 llama-server로 전환했다. API Key를 사용하고 외부에는 필요한 포트만 열어 OpenAI-compatible API를 제공했다. 

.\llama-server.exe `
  -hf ggml-org/Qwen3.8-27B-GGUF:Q4_K_M `
  --no-mmproj `
  -ngl all `
  -c 32768 `
  -np 1 `
  -fa on `
  --alias qwen3.8-27b `
  --host 0.0.0.0 `
  --port <PORT> `
  --api-key <API_KEY>
6

MacBook과 Windows 서버 연결

Network

Windows의 네트워크를 신뢰 LAN 환경에 맞게 구성하고 서버 주소를 고정했다. 이후 MacBook에서 /health와 모델 API를 호출해 두 장비 사이의 LAN 연결이 정상인지 확인했다. 

curl http://<AI-SERVER-LAN-IP>:<PORT>/health
# {"status":"ok"}
7

OpenCode Custom Provider 연결

Agent

MacBook에 OpenCode를 설치하고 OpenAI-compatible provider를 통해 Windows의 Qwen3.8-27B를 기본 모델로 연결했다. 초기 설정 스키마 차이와 권한 문제를 정리한 뒤 모델 인식까지 완료했다.

8

API Key 전달 방식 안정화

Auth

OpenCode에서 API Key가 안정적으로 전달되지 않는 문제가 있었고, 서버·네트워크 문제가 아니라 클라이언트의 credential 전달 방식으로 범위를 좁혔다. 최종적으로 API Key를 Mac 사용자 전용 Secret 파일에 보관하고 OpenCode가 파일을 참조하도록 구성했다. 

~/.secrets/llama-api-key
chmod 600 ~/.secrets/llama-api-key

실제 키 값과 내부 서버 주소는 공개 Work Log에 기록하지 않는다.

9

실제 Unity 저장소 분석

Repository

마지막으로 샘플 코드가 아니라 실제 Unity 프로젝트를 대상으로 파일을 수정하지 않고 구조를 분석하도록 요청했다. OpenCode/Qwen은 Glob과 Read를 사용해 주요 C# 파일을 찾아 읽고 게임플레이 구조를 설명했다. 

Examine this Unity project. Do not modify any files.
Identify the main gameplay architecture and the most important C# scripts.

결과: 로컬 코딩 AI 에이전트가 실제 Repository를 탐색하고 관련 코드를 선택해 읽는 단계까지 정상 동작했다.

10

32K Context에서 Compaction 확인

Observation

여러 코드 파일을 연속해서 읽는 과정에서 OpenCode의 Compaction이 발생했다. 따라서 32K Context는 기본적인 저장소 분석에는 사용할 수 있지만, 장시간 코딩 에이전트 작업에서는 Context 여유를 더 확보할 필요가 있다는 다음 검증 과제를 얻었다.

다음 과정

인프라 구축과 Repository 분석은 완료했다. 다음부터는 로컬 코딩 AI 에이전트가 실제 개발 작업을 어디까지 끝낼 수 있는지 검증한다.

1

기존 프로젝트에 실제 기능 추가

샘플 파일 생성이 아니라 기존 Unity 코드베이스를 읽고, 현재 규칙을 재사용하는 작은 기능을 직접 구현하게 한다.

2

수정 → 테스트 → Diff 검증

파일 수정에서 끝내지 않고 Unity 테스트 실행, 오류 분석과 재수정, git diff 검토까지 하나의 작업 루프로 수행할 수 있는지 확인한다.

3

Context 확장 효과 측정

32K에서 확인된 Compaction을 기준점으로 삼아 더 큰 Context에서 작업 지속성, VRAM 사용량, Agent 작업 여유가 어떻게 달라지는지 별도 벤치마크한다.
