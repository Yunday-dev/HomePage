작업 목표

이번 작업의 목표는 Qwen3.8-27B 기반 로컬 코딩 AI 에이전트가 기존 Unity 프로젝트의 코드베이스를 이해한 뒤, 현재 구조와 규칙을 깨뜨리지 않고 실제 기능을 추가할 수 있는지 확인하는 것이다. 새 샘플 프로젝트나 독립 예제가 아니라 이미 여러 시스템과 테스트가 존재하는 실제 프로젝트를 대상으로 했다.

첫 테스트 기능 — 유닛 생산 가능 여부 조회

첫 과제는 CanProduce(UnitType) 형태의 유닛 생산 가능 여부 조회 기능으로 제한했다. 현재 Food, Population, 게임 상태 등 기존 생산 조건을 확인해 “지금 이 유닛을 생산할 수 있는가”만 반환하고, 실제 자원 차감이나 유닛 생성처럼 게임 상태를 바꾸지는 않는 기능이다.

핵심은 새 규칙을 만드는 것이 아니라, 프로젝트 안에 이미 존재하는 TryProduce 계열의 생산 규칙과 관련 모델을 찾아 동일한 판단 기준을 중복 없이 재사용하는 것이었다. 따라서 코드베이스를 제대로 읽지 못하면 겉보기에는 동작해도 기존 규칙과 쉽게 어긋날 수 있다.

평가 기준: 코드 한 조각을 생성하는지가 아니라 관련 코드 탐색 → 기존 규칙 파악 → 최소 범위 구현 → 테스트 추가 → Unity 테스트 실행 → 실패 시 수정 → Git diff 검토까지 하나의 작업 루프로 완료할 수 있는지를 본다.

왜 가장 단순한 기능부터 시작했나

1. 코드 이해 능력을 분리해서 보기 위해
입력·UI·애니메이션 같은 구현 복잡도를 줄이고 기존 규칙을 정확히 찾는 능력에 집중한다.

2. 변경 위험을 낮추기 위해
조회 전용 기능이라 실패해도 게임 상태를 직접 훼손할 가능성이 낮다.

3. 결과를 객관적으로 검증하기 위해
기존 생산 조건과 테스트를 기준으로 정답 여부를 명확하게 판정할 수 있다.

4. 이후 난이도를 단계적으로 올리기 위해
작은 성공을 baseline으로 삼아 다음에는 여러 시스템이 연결되는 기능으로 확장할 수 있다.

64K / 128K Context 벤치마크

기능 구현 결과와 별도로, Context 크기에 따른 작업 여유와 메모리 사용량을 비교했다.

위의 기능 검증과는 별도로, 같은 Qwen3.8-27B 모델에서 Context 크기만 바꿔 로컬 코딩 AI 에이전트의 작업 여유를 비교했다. 두 설정 모두 기능 구현과 전체 EditMode 테스트까지 완료했다. 또한 모델 로딩 직후의 동일한 유휴 상태에서 GPU VRAM과 Windows 시스템 메모리를 측정해, Context 확장이 실제 메모리 비용에 어떤 차이를 만드는지도 함께 확인했다.

관찰된 특성작업 완료는 가능하지만 긴 탐색에서 Context 압박 발생같은 계열 작업을 Compaction 없이 유지할 여유 확보
메모리 관찰: 모델 로딩 직후 기준으로 64K는 약 23.7 GiB, 128K는 약 27.9 GiB의 GPU VRAM을 사용했다. Context를 2배로 늘리면서 VRAM은 약 4.26 GiB, 약 18% 증가했지만 Windows 전체 시스템 메모리는 두 측정 모두 29.9 / 61.7 GB로 거의 동일했다. 즉 이번 구성에서는 Context 확장의 추가 메모리 비용이 주로 GPU의 KV cache 영역에 나타난 것으로 볼 수 있다.
RTX 5090에서의 128K 적재: 측정 당시 128K 설정은 총 32,607 MiB 가운데 28,588 MiB를 사용해 RTX 5090의 전용 VRAM 안에 정상적으로 적재되었고 약 4,019 MiB, 약 3.9 GiB의 여유가 남았다. 따라서 Qwen3.8-27B Q4_K_M을 단일 모델·단일 작업 환경으로 운용할 때 128K Context도 RTX 5090 32GB에서 실사용 가능한 범위다. 다만 다른 GPU 작업을 동시에 실행할 경우에는 남은 VRAM 여유를 고려할 필요가 있다.
현재 결론: 작은 코드 수정은 64K로도 충분히 완료할 수 있었지만, 문서·코드·테스트를 연속해서 읽는 자율 로컬 코딩 AI 에이전트 작업에서는 128K가 Context 압박을 줄였다. 동시에 128K도 RTX 5090 VRAM 안에 적재할 수 있었으므로, 현재 Qwen3.8-27B 기반 로컬 코딩 AI 에이전트의 장시간 작업용 Context로 실제 운용이 가능하다는 점을 확인했다.

개발 환경 안정화

기능 검증과 별개로 로컬 코딩 AI 에이전트가 Unity 저장소를 반복해서 수정·테스트할 수 있도록 실행 권한과 로컬 모델 서버 운영 방식을 정리했다.

OpenCode 권한 및 파일 소유권 정리

초기 권한 오류를 피하려고 관리자 권한으로 OpenCode를 실행했던 과정에서 Unity가 생성한 일부 파일까지 관리자 소유가 되는 문제가 발생했다.

OpenCode 사용자 디렉터리와 프로젝트 파일 소유권을 정상 사용자로 복구하고, 이후 OpenCode·Unity·Git을 모두 일반 사용자 권한으로 실행하는 것을 기본 원칙으로 정리했다.

목표: 로컬 코딩 AI 에이전트가 파일을 생성하거나 Unity batchmode를 실행하더라도 저장소 안의 파일 소유권이 뒤섞이지 않는 일관된 개발 환경을 유지한다.

PowerShell $PROFILE에 llama-server 제어 함수 등록

Windows PowerShell의 $PROFILE에 로컬 모델 서버의 시작·종료 명령을 PowerShell 프로필 함수로 등록했다.

매번 긴 llama-server 실행 옵션을 입력하지 않고 모델·Context·GPU 설정을 정해진 함수 호출로 실행할 수 있게 해 반복적인 테스트 환경 구성을 단순화했다.

작업 과정

처음부터 복잡한 기능을 맡기기보다, 코드베이스 이해 여부를 확인하기 좋은 작은 기능을 선정하고 로컬 코딩 AI 에이전트가 실제 개발 작업의 전체 흐름을 얼마나 자율적으로 수행하는지 단계별로 확인했다.

1

기존 프로젝트에서 테스트 과제 선정

Scope

새 예제를 만들지 않고 현재 Unity 프로젝트의 생산 시스템에 CanProduce(UnitType) 조회 기능을 추가하는 과제를 선택했다. 범위는 작지만 정답을 만들려면 기존 Food·Population·게임 상태 관련 규칙을 먼저 찾아야 한다.

2

관련 코드와 테스트 탐색

Understand

로컬 코딩 AI 에이전트가 생산을 담당하는 클래스, 데이터 모델, 기존 TryProduce 흐름과 테스트를 읽고 어떤 조건이 실제 생산 가능 여부를 결정하는지 파악하도록 했다.

확인 포인트: 비슷한 조건문을 새로 작성하는 대신 프로젝트에 이미 존재하는 규칙과 책임 경계를 찾아낼 수 있는가.

3

상태를 변경하지 않는 조회 경로 구현

Edit

기존 생산 규칙을 이용해 유닛 생산 가능 여부만 반환하도록 구현했다. Food 차감, Population 변경, 실제 유닛 생성, HUD 출력 같은 부수 효과는 발생하지 않도록 범위를 제한했다.

결과: 작은 변경이지만 기존 시스템의 의미를 이해해야 구현할 수 있는 기능을 실제 코드베이스에 추가했다.

4

자동 테스트와 실패 복구

Test

신규 기능을 검증하는 focused EditMode 테스트를 실행한 뒤 전체 EditMode suite까지 돌려 기존 기능의 회귀가 없는지 확인했다. 테스트 실패나 환경 문제는 원인을 다시 추적해 수정하도록 했다.

5

Git diff로 최종 변경 범위 확인

Diff

git diff --check와 최종 diff를 확인해 의도한 코드·테스트 외에 Unity가 자동으로 만든 변경이나 불필요한 수정이 섞이지 않았는지 검토했다.

결론: Qwen3.8-27B 기반 로컬 코딩 AI 에이전트가 기존 코드베이스를 읽고 작은 기능을 구현한 뒤 검증까지 끝내는 실전 작업 루프를 수행할 수 있음을 확인했다.

다음 과정

작은 조회 기능은 통과했다. 다음 과정에서는 입력·카메라·이동·타깃·공격처럼 여러 시스템이 동시에 연결되는 실제 기능을 맡겨 로컬 코딩 AI 에이전트가 더 복잡한 코드베이스에서도 구현과 검증을 끝까지 수행할 수 있는지 확인한다.

1

플레이어 이동·공격 명령 구현

전투 화면의 빈 공간을 클릭하면 플레이어 캐릭터가 해당 위치로 이동하고, 적을 클릭하면 그 적을 공격 대상으로 지정하도록 만든다.

단순 조회 함수와 달리 입력 처리, UI 클릭 구분, 화면 좌표→월드 좌표 변환, 이동 상태, 공격 타깃, 기존 자동 전투와의 분리가 동시에 필요하다.

2

PlayMode 자동 테스트 확대

로컬 코딩 AI 에이전트가 Unity PlayMode 테스트를 작성하고 batchmode에서 직접 실행하도록 검증 범위를 넓힌다. 상태 전환이나 이동·공격 로직처럼 코드로 판정할 수 있는 동작은 자동 테스트로 확인한다.

EditMode 테스트만으로 확인하기 어려운 런타임 객체 생성, 프레임 진행, 입력 처리 경로 등을 에이전트가 자동으로 재현하고 검증할 수 있는 기반을 만든다.

3

실제 Game View 검증과 디버깅 루프

마우스 클릭 감각, 카메라 동작, UI raycast, 화면상 이동 결과처럼 실제 화면을 봐야 확실히 판단할 수 있는 부분은 Game View에서 직접 확인한다.

현재 OpenCode 기반 로컬 코딩 AI 에이전트는 Game View를 사람처럼 직접 보고 조작하는 단계까지는 포함하지 않는다. 대신 실제 실행에서 발견된 현상과 로그를 다시 전달해 원인을 추적하고 수정하는 디버깅 루프까지 연결한다.
